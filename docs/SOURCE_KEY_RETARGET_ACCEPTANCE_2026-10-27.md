## Behavior

Retarget Options offers **Dense Next (default)**, **Source bone keys** and
**Source channel keys**. The setting belongs to the current application session.
It does not create document edits or replace project state. The result records
its chosen representation as bounded, additive historical recipe evidence;
older projects without these fields retain Dense behavior and schema 1.

Dense executes the original Next solver and writer path. Source-key modes first
freeze that complete result, then project target-space values and tangents onto
the requested source schedule. They never copy a donor's local pose values onto
an unequal target bind. Unmapped/source-only bone tracks are omitted. Reviewed
motion controls retain their existing exact own-source local curves, paired
sides and any required coordinate-conversion keys in every mode.

Source bone keys use the union of a mapped source bone's authored knot times,
including paired multiplicity, on each necessary target S/R/T group. Entire
bind-equivalent groups stay absent. Native CHR0 stores complete groups; necessary
groups retain all three axes. Source channel keys keep each individual source
channel's times/counts and absent groups. Unsupported in-memory partial-axis
groups and single fixed keys away from frame zero are explicitly rejected rather
than silently gaining replacement keys. No new zero-key native payload format is
invented, and no game safety is inferred from a reader accepting such a payload.

The non-Dense UI freezes the live source's semantic content, exports an independent
precise copy and verifies its decoded identity. It never rebuilds the live source
through the legacy quantized/per-frame selector. Stale-source checks also compare
live semantic content. A dirty ordinary native fixture with interpolation
preservation disabled proves that the legacy writer changes its source schedule,
while this path retains the visible authored keys, codec preference, native dirty
state and Undo. Dense keeps its prior export/hash snapshot path unchanged.

Sparse results must pass independent precise CHR0 encode/reopen of their complete
metadata, flags, order, knot indices, duplicate sides, values and tangents. The
application measures every native target bone and skinned vertex against the
frozen dense result at native integer/quarter times, withheld .37/.73 witnesses,
paired-knot neighbors, stored-loop closing samples and bind pose. Existing
100,000-witness / ten-million-bone / one-billion-vertex budgets, the two-million-key
limit and cancellation remain enforced. Budget failure yields no partial result.
These are sampled differences; no continuous quality certificate is claimed.

A read-only comparison shows the original dense target and prepared sparse target,
native key/byte counts, observed Euler/orientation/local/world/skin drift, omitted
tracks/channels and protected controls. The user must review the result explicitly
before adding an independent target revision. Cancelled or stale preparation adds
nothing. Playback evaluates owned prepared native curves without loading,
rehashing, baking or solving. Existing native project-import Undo is reused.

When trim/timing fitting is selected, the schedule belongs to that explicitly
resampled preparation. It does not promise unchanged original pre-fit key times.

Dense contact/limb statistics are retained separately as historical reference
evidence. They cannot qualify changed sparse curves as protected support paths;
ordinary native editing and fitting remain available. Subsequent optimization or
native edits preserve the historical source-key receipt rather than rewriting
its original result hashes. Review recipe signatures include the chosen mode,
comparison and historical statistics. Advanced Scene / Body Fitting's explicit
Original Next action always forces Dense.

## Boundaries

The full BrawlCrate Model Previewer, original dense Next default, native Undo and
source-owned root policy remain intact. Brawl CHR0 v4/v5 is the native boundary.
Fresh precise standalone byte counts are separate from PAC/container/compression
savings. There is no universal Brawl/Melee byte budget. Melee needs its separate
native writing/evaluation adapter. Physical input, monitor DPI, human usability,
general contact quality, additional games and actual game acceptance remain
unverified. No second document/Undo owner, automatic optimization, skeleton
replacement or project-format migration is introduced.
