## CHR0 research prompted by the size regression

The complete local report is
`artifacts/Fighterport-unified54/chr0-research/index.html`, with file/channel CSVs,
byte offsets, hashes and the read-only probe source. Findings:

- The current 44,768-byte Mario result has **39 tracks / 3,852 logical keys**,
  all matching actual Mario bones. Sonic has 66 tracks / 4,444 projected keys.
  Absent source bones are already removed.
- The same Sonic editor projection written with precise I12 is **55,488 bytes**,
  with the same 66 tracks and 4,444 keys, without retargeting. The original uses
  dense L1 and compact I4. Encoding is a dominant independent cost.
- Current key payload is **39,202 bytes**, versus the original's 5,904. Net
  growth is exactly 33,298 bytes more payload minus 546 bytes less overhead.
- Current fractional correction generates **741 extra paired sides** across
  96 rotation channels, absent in the donor. Their direct I12 cost is 8,892
  bytes. Each paired knot has a tangent outside the exact I6 grid. Current
  paired-side protections also exclude dense proposals and force exactness;
  blindly deleting those different tangents is not exact cleanup.
- A complete independent probe of **all 84 original dense channels**, 44 whole
  frames and 301 fractional witnesses compares native generated-tangent
  interpolation with reference dense linear interpolation. Whole-frame local
  values, joint positions and all native weighted positions match; fractional
  differences reach **30.97192° raw Euler / 31.66269° local orientation** and
  **2.28716 native units at skinned vertices**. This supersedes the preliminary
  six-channel diagnostic. Direct storage-plan diagnosis accepts all 84 original
  dense payloads and all their value bits, but **52 channels fail reconstructed
  tangent-bit matching**. Entry-wide rejection leaves only two complete
  three-axis entries (6/84 channels) adopted by the storage-capture helper.
  Correct and independently qualify the tangent reconstruction; do not bypass
  layout or matching guards.

The [BrawlCrate decoder](https://github.com/soopercool101/BrawlCrate/blob/master/BrawlLib/Wii/Animations/AnimationConverter.cs)
generates native tangents from dense samples. The
[NW4R reference runtime](https://github.com/doldecomp/ogws/blob/master/src/nw4r/g3d/res/g3d_resanmchr.cpp)
uses linear dense evaluation and supports fractional indexed times. This is
reference-runtime evidence, **not Brawl executable qualification**. The editor's
integer key representation must not be described as an inherent CHR0 limit.
The inference is that incompatible evaluation expectations can reject compact
storage and manufacture corrective tangent data. Establish a codec-aware oracle
and storage-capture rejection diagnostics before more numerical tuning; preserve
Next's solver, native editing, exact root functions and the frozen quality caps.
